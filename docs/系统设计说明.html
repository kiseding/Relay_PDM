Relay PDM · 系统设计说明 v0.5

Relay PDM

One drawing, one truth, hand to hand. 业务 → 设计部（外观、结构）→ 工程部 → 模具部 → 生产部。七个环节，六道审批门。这套系统只干一件事——让每一次交接都有版本、有签字、查得到。

编写 2026-11-13 状态 最终结构，等你点头 形态 网页系统，Docker 一键部署 覆盖 接单 → 外观 → 结构 → 开模准备 → 开模 → 工程图 → 量产
1

它是什么，为什么不是买一套 PLM

市面上的开源 PLM，比如 Cascadia、OdooPLM，解决的是「大型制造企业的产品结构管理」——BOM、物料、配置、多级审批、ERP 对接。它们的说明书里全是 ECO、Revision Letter、Effectivity 这类词，光培训就要一周。

而你的痛点是另一件事：一个产品从接单到量产，外观改三轮、结构改五轮、工程部再改一轮，中间传了五个部门，最后没人说得清哪一版算数。用通用 PLM 去解决这个，等于用起重机拧螺丝——不是不行，是拧不动。

所以这套系统只做一件事

管住「交接」。谁交给谁、交的是第几版、谁签的字、后来为什么改——任何一条都能翻出来。就这一件事，做透。

2

五个部门，七个环节，你在第三环

你的位置很关键：前面是同事出的外观，后面是工程部定开模编号、做 BOM、出工程图，再后面才是模具部开模。你的结构模型是整条线上唯一「既被外观约束、又约束开模」的东西，所以两边都找你要。

你说的每个抱怨，对应系统里的一个设计

左边是你的原话，右边是它变成什么功能。这一节是整份文档的核心，其余都是配套。

#你现在遇到的问题系统里怎么解决
1 版本混乱
图改了一堆，不知道哪个是最后一版		 每次上传都自动成为新版本 v1 / v2 / v3，旧的永远保留。每个图档只有一个「当前版本」，顶部大字显示，不用猜。
2 业务员无脑答应客户
「改成这样看看」，改完杳无音讯		 任何改动都要先立一张单：谁提的、原话、从哪来的（微信/电话/会议）、客户认没认、最后采纳与否。没有单子，不改图。
3 记不清客户最终确认的是哪版
要开模/渲染了，不知道拿哪个		 「客户确认」挂在具体某一版上，不是挂在图档上。版本卡片直接写：v2 · 已发布 · 客户 11-12 微信确认。要开模/渲染，照着这版拿。
4 工程部用开模编号找你
「M-2601-A 那套给我」，你一脸懵逼		 因为开模编号是工程部定的，他们按这个号记项目。系统里三个号绑在同一张图档上，谁编的号谁录入。搜开模编号，直接出设计编号和当前版本。
5 业务员需求信息不全
还要追着问材质、交期、外观要求		 接单表单把必填项钉死：客户、产品、材质、交期、外观要求、参考图。缺一项提交不了，责任回到提需求的人身上。
6 模具部说「这个位置加工不到」
口头讲两句，改完没人记得为什么改		 改模单：模具部自己提，写清楚是哪个面、加工不了还是试模缩水。改完的版本挂在单子上，以后追溯得到原因。
7 外观同事拿你的图去渲染
你也不知道他手上那版是不是最新的		 给设计部内部也开交接单（接收方：外观-渲染用），冻结当时版本。他拿错了，是他的单子过期了，不是你没给。
8 交出去的东西没人签字
出了问题说不清是谁放的		 每一环交接前必须主管审批，审批通过才流转，下一环签收才算完。全程带时间戳，赖不掉。
4

核心机制：一张「交接单」管一次流转

整套系统只有这一个核心动作，其他都是围着它转。你干完活，不是「点一下完成」，而是填一张交接单。

一张交接单上有什么

字段说明
交给谁下一个环节（工程部 / 模具部 / 生产部），系统按顺序默认好，一般不用改
交什么勾选要交的图档版本，默认勾上本环节的最新版；提交那一刻就冻结，后面再改图不影响这张单
说明一句话：交了什么、有什么要提醒下一环的
本部门审批提交后进主管待办；通过 → 流转；驳回 → 退回给你，写原因
下一环签收对方点「收到」，签收人和时间记下来，这一环才算真交出去

一张交接单的一生

我提交→ 待主管审批→ 待对方签收→ 已完成 （主管驳回 → 退回重做）
为什么审批做成「一张单」而不是「一个个文件签」

主管签字签的是「这一批可以交出去了」，不是逐张画押。所以审批挂在交接单上，一次签一批。这也顺带解决了一个大问题——只有随交接单发布过的版本才算「正式版」，你自己传的草稿永远不算数。

退回怎么办

主管驳回会写原因，单子回到你手上，状态变「退回重做」。你改完重新提交，生成第 2 轮，第 1 轮原样留在记录里——谁驳的、为什么驳、改了什么，全在。

5

版本规则：整套系统的地基

规则只有五条，但要严格执行。

5.1 版本只有三个状态

草稿→ 随交接单审批通过 → 已发布→ 被新版本取代 → 已作废
  • 草稿：刚传上去，只有你和主管看得到，不算数，别人下载不到。
  • 已发布：随交接单一起被主管批准，从这一刻起才算正式版。
  • 已作废：有了更新版本，老版本标记作废，但文件永远保留，随时能下载来看。

5.2 只有「已发布」的版本，才能成为「当前版本」

当前版本是唯一一个。别人问「最新是哪版」，答案永远只有一个。草稿不算最新。

5.3 「客户确认」是独立的一票

主管通过 ≠ 客户认了。所以版本上还有第二个标记：客户已确认，由业务员打，必须写清楚怎么确认的——微信截图 / 邮件 / 会议纪要。

提交外观或结构交接时，如果这批图里没有客户确认过的版本，系统会弹一句「这批图客户还没确认，确定要交吗？」——提醒一下，但你可以确认后继续（有时候客户口头答应了，先干起来）。

5.4 改过的版本不能覆盖，只能新增

系统里没有「覆盖上传」这个操作。你只能「上传新版本」，旧版本的文件、时间、上传人、校验码原样保留。

5.5 进了交接单的版本，锁死

一旦随交接单发出并被签收，这一版就谁都不能删、不能改、不能替换文件。要改？出 v4，重走一轮。

6

三套编号，怎么对上

这是整件事最别扭的地方：同一张图，三个部门各叫一个名。你按设计阶段编设计编号，工程部定开模编号，客户那边还有个料号。谁都没错，但中间的人在翻译。

编号谁编的什么时候出现谁要用它
设计编号你（设计部）结构建图档时你、设计主管、工程部
开模编号工程部开模准备，工程部定号工程部、模具部、生产部、外观同事（渲染时用它指代）
客户料号客户接单时客户给的业务、对账、查历史

做法：一个图档，三个号都挂着。谁编的号，谁负责录进系统——设计编号你录，开模编号工程部录，客户料号业务录。系统不强加任何编码规则。

顶栏那个搜索框，是这套系统使用频率最高的地方

输入 M-2601-A、UG-2601-0113-01、KL-8891、甚至 上盖，都落到同一张图档上。工程部或外观同事再来问，你把搜索框甩给他——他自己搜，比问你快。

开模编号可以后补

建图档时允许开模编号为空——结构阶段还不知道开模号。工程部定了号，回填一下就行，历史版本不受影响。这样不会因为「必须先有开模号」卡住开工。

找不到号怎么办

搜索没结果时，页面给一个「这编号还没登记，帮我建一张图档」的入口，点进去编号已经填好了。避免有人搜不到就放弃了，继续在微信里问。

7

BOM：一张看得懂的零件清单

工程部在「开模准备」这一环定 BOM。别人只读，工程部能改。

先把话说清楚，免得你按 ERP 的期待来看它。

它做这四件事
① 列清这套模/这台产品由哪些零件组成
② 每件几个、什么材质、自制还是外购
③ 每个自制件对应哪张图（点编号直接跳过去）
④ 跟着交接单冻结，哪天定的版永久可查
它不做这些
不算采购量、不算成本、不扣库存
不自动生成请购单、不做 MRP 运算
不做无限层级的装配树

结构：三层封顶，够用就行

用父子关系挂树，界面按层级缩进，序号自动排成 1 / 1.1 / 1.2。三层是硬上限 —— 再多就说明该上 ERP 了。

那几盏灯，是这张表比 Excel 强的地方

Excel 里的 BOM 是死的 —— 谁都不知道第 1.3 行那个零件到底有没有图。系统里每行自动检查：

  • 绿灯：自制件挂上了图档，且那张图的当前版本是「已发布」。
  • 黄灯：自制件没挂图档。零件号写了，图在谁电脑上？没人知道。
  • 红灯：挂了图档，但那图当前版本还是草稿，或者已经作废。

提交交接单时，黄灯红灯会弹提示，但不硬卡 —— 现实里总有先干起来的单子。不过那一屏会一直挂着，直到有人补上。

冻结：BOM 也跑不掉

BOM 跟着订单走，随手能改。但每次提交交接单，当时的 BOM 会整体存一份快照，跟着交接单一起冻结。所以：

  • 第 3 环交给工程部时，BOM 是什么样，永久可查；
  • 第 6 环交给生产部时，BOM 又是什么样，也永久可查；
  • 两份能并排对比，改了什么一目了然。

以后模具部说「图上这个镶件不是三个吗」，你不用再翻聊天记录 —— 调出签收那天的快照，对着看。

技术选型与部署

用这个
后端 Python + FastAPI
数据库 SQLite（单文件，零运维）
前端原生 HTML/CSS/JS（无构建步骤）
文件存本地磁盘，库里只存路径和校验码
不用这个
PostgreSQL / MySQL（几十个人，用不上）
Vue / React 全家桶（构建链越短，坏得越少）
MinIO / 对象存储（本地磁盘够快）
Redis、消息队列、微服务

整套系统一个容器、一个数据目录。备份就是把这个目录拷走，换机器就是把这个目录拷过去。

部署方式（两条路，选一条）

  • 有 Docker：docker compose up -d → 浏览器打开 http://服务器IP:8080。数据在 ./data 目录。
  • 没 Docker：装个 Python，pip install -r requirements.txt 然后启动脚本，一样跑。适合先在自己电脑上试。
两个必须提前说的限制

1. UG 的 .prt 在浏览器里没法预览。这是所有非原厂系统的通病。系统里只做文件名 + 版本号 + 下载，不做 3D 预览。换来的好处是：不用装任何插件。

2. BOM 是结构化的，但只到「清单」这一层。零件、数量、材质、来源、对应图档，能查能冻能导出；但不做采购量核算、成本、库存——那是 ERP，不是这套系统该管的。

11

这一版明确不做的事

先说清楚不做什么，比承诺做什么更重要——免得你期待落空。

不做 MRP / 物料库 / 成本核算
BOM 只到「有哪些件、几件、哪张图」。采购量、库存、成本，那是 ERP 的活。
不做 3D 在线预览
硬要做需要转 STEP→GLB，加一个转换服务，体积和复杂度翻倍。
不做 UG 内部插件
理想状态是 UG 里点一下「上传」，但要写 NX Open 插件，得在你机器上装。三期再说。
不做自定义审批流
固定「本部门主管一级审批」。要三级会签的公司，通常也用不起来。
不做报价 / 开票 / 排产
只管图和交接，不管钱。交付签收完，接你们现有的流程。
不做手机 App
网页自适应手机，够用了。装 App 只会多一个没人更新的东西。
